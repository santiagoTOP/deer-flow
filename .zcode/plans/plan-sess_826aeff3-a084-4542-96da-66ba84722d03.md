## 文档结构

### 开篇
- 标题：`lifespan 深度讲解：为什么不能直接在 import 时 `checkpointer = PostgresSaver(...)` 就完事`
- 系列导语：承接三篇姊妹篇（StreamBridge/RunManager/get_checkpointer），点明这篇讲的是它们全部"放进工具箱/取出工具箱"的**总闸**——那个总闸就是 lifespan。

### 第 0 步：前置概念（带 ※ 标记复用姊妹篇）
- **0.1 lifespan = 开机/关机的总闸**（`@asynccontextmanager` + `yield` 前后语义；`AsyncGenerator[None, None]` 的含义）—— 复用 get-checkpointer §0.4，聚焦 yield 前后。
- **0.2 import-time vs startup-time**（★本篇核心概念）：Python 模块在第一次 `import` 时执行模块顶层代码（import-time），而 lifespan 里的代码是 uvicorn 启动应用时才执行（startup-time）。两者差一个生命周期，朴素写法把"该 startup 做的事"写在 import 层，就埋下全部雷。
- **0.3 `app.state` 进程级工具箱**（※ 复用 get-checkpointer §0.3，本篇只复用结论）。
- **0.4 `AsyncExitStack` + LIFO teardown**：`async with` 嵌套/`AsyncExitStack` 的关闭顺序是"后进先出"（后开的先关），这是嵌套资源关闭顺序正确性的基石。
- **0.5 "持资源对象" vs "纯数据对象"**：checkpointer / DB engine / stream bridge 这些持有数据库连接、文件句柄、单例 provider，是"会占用外部资源"的对象，不能像 `dict()` 随手 new、随手丢——它们的生命周期必须被显式管。
- **0.6 bounded shutdown + uvicorn graceful 预算**：`asyncio.wait_for(..., timeout)` 把每个关机钩子套进有界等待，否则一个卡住的钩子会拖死整个 worker 退出，触发 SIGTERM→SIGKILL 风暴。
- **0.7 启动步骤的致命/非致命分级**：哪些失败必须 `raise`（拒绝启动），哪些 `try/except + log`（继续服务）——这是 startup 容错的总策略。

### 第 1 步：朴素写法长什么样（反面教材）
模拟"把所有初始化写在模块顶层、不用 lifespan"的写法：
```python
# app.py 模块顶层（import 时执行）
config = get_app_config()              # import 时读 config.yaml
checkpointer = PostgresSaver(conn=...)  # import 时开数据库连接
run_manager = RunManager(...)
app = FastAPI()                         # 没有 lifespan=
```
逐行解释 + 4 类崩点：
- config.yaml 还没生成（import 时文件不在）→ import 直接崩，连 /setup 都进不去。
- 数据库连接在 import 时就开 → 跑测试时 import 一次 app 就开一个连接池，连接泄漏；多 worker 各 import 各开，连接数爆炸。
- 没有关闭路径 → 连接池永远不关，进程退出时资源泄漏；in-flight run task 写半截 checkpoint（#3373）。
- 无法替换 → 测试无法注入 mock checkpointer / mock run_manager。

点明：RunManager 那篇讲的是"run 的执行生命周期 vs 请求生命周期"的解耦；**本篇讲的是"资源的生命周期 vs 模块/进程的生命周期"的解耦**——两个解耦同一个总闸（lifespan）在做。

### 第 2 步：N 个麻烦逐一展开（每段贴真实代码 + 逐行解释）
- **麻烦 1：config 必须在 startup 时读，且故意不缓存到 app.state**
  贴 `app.py:174-191`（`startup_config = get_app_config()` + 注释）。讲：① config.yaml 是运行时文件，import 时可能不存在；② `startup_config` 是局部快照只用于一次性 bootstrap；③ 故意 **不** 挂到 app.state，是为了让"请求时永远走 `get_config()` 重读 config.yaml"这个 hot-reload 契约不被破坏。失败时 `raise RuntimeError`（致命，拒绝启动）。
- **麻烦 2：副作用必须在 startup 时发生（logging / Monocle / tiktoken 预热）**
  贴 `app.py:193-237`。讲：① `configure_logging` 要先有 config 才能配；② Monocle tracing 明确注释"startup 时初始化而非 import 时，避免 plain `import deerflow.agents` 装一个进程级 tracer"——这是 import-time vs startup-time 的直接例证；③ tiktoken 预热是非致命 + 5s 有界等待 + char-mode 后端跳过（避免受限网络下打 OpenAI URL）。讲这三段都"失败不致命"的分级（observability/预热/cleanup 都包了 try/except）。
- **麻烦 3：嵌套 `langgraph_runtime` —— yield 在它内部，资源交给 AsyncExitStack**
  贴 `deps.py:222-258`（langgraph_runtime 骨架）+ `app.py:239-241`（`async with langgraph_runtime(...)`）。讲：① lifespan 自己的 `yield`（`app.py:275`）其实在 `langgraph_runtime` 的 `yield`（`deps.py:332`）内部——两层 async context manager 嵌套；② `langgraph_runtime` 用 `AsyncExitStack` 把 stream_bridge/checkpointer/store/RunManager 一个个 enter，关闭时 LIFO 自动 teardown；③ 为什么这套要用 AsyncExitStack 而不是手写一堆 `try/finally`（正确性、异常安全）；④ 多 worker Postgres 门（`_enforce_postgres_for_multi_worker`，呼应 run-manager §0.8）。
- **麻烦 4：#3373 —— 为什么 yield 必须在 langgraph_runtime 内部、drain 必须在 close_engine 之前**
  贴 `deps.py:332-343`（langgraph_runtime 的 finally）+ `deps.py:88-111`（`_drain_inflight_runs` 带 `asyncio.shield`）。讲 issue #3373 的根：langgraph 的 `_checkpointer_put_after_previous` 在独立后台 task 里 `aput` 写 checkpoint，若进程退出时连接池先关，那个 aput 撞已关闭 pool 抛 `PoolClosed`，且这个异常 run_agent 的 try/except 抓不到。修法：yield 放在 langgraph_runtime 内、finally 先 `await _drain_inflight_runs(run_manager)` 再 `await close_engine()`——drain 时连接池还没关，run 能干净 flush 最后一个 checkpoint。呼应 run-manager 麻烦 6（shutdown）。
- **麻烦 5：启动步骤的顺序依赖（"谁必须排在谁之后"）**
  贴 `app.py:243-273`。讲：① `_ensure_admin_user(app)` 必须在 `langgraph_runtime` 之后，因为它要用 `app.state.store` 迁移孤儿 thread；② channels / scheduler 也都在 `langgraph_runtime` 之后（要用 run_manager / repos）；③ scheduler 只在 `app.state.scheduled_task_repo` 和 `scheduled_task_run_repo` 都存在时才建，且只在 `scheduler.enabled` 时才 `.start()`——"构造"和"启动"分开，关机时无条件 `.stop()`。讲这种"依赖图 + 守卫"的有序启动。
- **麻烦 6：关机顺序 + bounded —— 反向收尾，每步有界**
  贴 `app.py:277-341`。逐行讲关机顺序：① `auth.close_oidc_service()`；② `stop_channel_service()` 套 `asyncio.wait_for(timeout=5s)`——解释为什么关机钩子必须有界（呼应 0.6，防止拖死 worker）；③ scheduler `.stop()`；④ memory `shutdown_flush` **必须在 langgraph_runtime 块内、channels/scheduler 已停之后**（注释明确：channels/scheduler 已停，没有新更新涌入；drain 在 pool 关闭前）；⑤ 最后才退出 `async with langgraph_runtime`（触发 deps.py 的 drain+close_engine）。讲"关机是开机的镜像 + 有界化"。
