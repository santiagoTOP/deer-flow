## 骨架（严格复刻姊妹篇 4 段结构）

**标题 + 开场**：点明这是第四篇姊妹篇，讲 `deps.py:368` 那一行。和前三篇（stream-bridge / run-manager / get-checkpointer）回答的是同一个大问题的不同面——前三篇讲 agent run 怎么"活过请求"，这篇讲一个**反向的、却同样要解耦**的场景：**不是进程级资源该不该活久，而是"有些功能本身就是可选的，没配 DB 时干脆别让它假装可用"**。预先点破 Feedback 与前三篇的本质差别——它没有连接池生命周期、没有关机顺序问题，它的麻烦落在另一个维度（可选性 / 隔离 / 幂等 / 读侧聚合）。

**第 0 步：术语铺垫**（带 ※ 标记可跳过姊妹篇讲过的）
- 0.1 ※ `app.state`——进程级工具箱（复用 checkpointer 篇结论）
- 0.2 ※ `_require` 工厂——取不到就 503（复用 checkpointer 篇 §麻烦6，因本文主角就是它的产出）
- 0.3 ※ lifespan——开机/关机总闸（复用）
- 0.4 **FeedbackRepository——仓库（本文新概念）**：类比"按用户分柜台的留言簿"，引出"仓库持有 session_factory，方法各自开短 session"
- 0.5 **`async_sessionmaker`——短命会话工厂**：类比"图书馆借阅证"，解释为何反馈仓库不像 checkpointer 那样需要长寿命连接池（每个方法 `async with self._sf()` 现借现还），这是 Feedback 的"轻"从何而来
- 0.6 **`resolve_user_id` / `AUTO` 哨兵——"当前调用者是谁"**：讲三态语义（AUTO 从 contextvar 取 / 显式 str 覆盖 / 显式 None 跳过过滤），它是多租户隔离的地基
- 0.7 **`UniqueConstraint(thread_id, run_id, user_id)`——一人一次只能打一次分**：类比"一个观众对一个节目只能投一票"
- 0.8 HTTP 503 / 409 / 400——这三种状态码在本篇分别什么时候出现（503=功能没启用；400=rating 非法；404=run 不存在；409 在 feedback 场景其实是 upsert 不出现的，点一下区别）

**第 1 步：朴素写法长什么样**（反面教材）

```python
async def upsert_feedback(thread_id, run_id, body):
    repo = FeedbackRepository(SomeSessionFactory())  # 每请求 new 一个工厂
    await repo.upsert(...)  # 不分用户、不查 run 存在不存在、不防重复
```

逐行解释，点出根本病根：把"仓库"当成随手 new 的临时对象，丢掉了①配置驱动的可用性边界 ②用户隔离 ③幂等。

**第 2 步：6 个麻烦逐一展开**（每个都按"场景 / 朴素写法为什么做不到 / DeerFlow 怎么解决 + 逐行代码"的三段式，完全平行于姊妹篇）

- **麻烦 1：没配数据库时，反馈功能该不该可用**
  - 场景：本地开发 / 纯内存模式没 DB
  - 朴素：要么写死假定有 DB（一访问就崩），要么无脑造个内存版（假装可用、数据却重启即丢、误导用户）
  - 解决：`deps.py:271-282` 的 if/else——有 DB 给真仓库，没 DB 显式 `app.state.feedback_repo = None`；`get_feedback_repo` 取到 None 就抛 **503 "Feedback not available"**。逐行讲 `_require` 闭包 + 为什么 503 比 NoneType 深层崩友好。对比 get_store（返回 None）为什么 Feedback 偏偏选 503（因为反馈是终端用户可见功能，不该静默退化）

- **麻烦 2：进程级单例 + 共享 session_factory，不能每次 new**
  - 场景：高频打分请求
  - 朴素：每请求 new `FeedbackRepository(自建session_factory())`，重复建工厂 / 连接
  - 解决：启动时 `app.state.feedback_repo = FeedbackRepository(sf)`（`deps.py:277`），全进程共用一个，`sf` 是和 RunRepository 同一个 session_factory（`deps.py:271` 注释 "one get_session_factory() call for all"）。讲清"为什么仓库本身是单例，但它内部的 session 不是"

- **麻烦 3：每个方法开短命 session，借完即还（为什么 Feedback 不需要连接池生命周期）**
  - 场景：并发打分 / 列表查询
  - 解释 `async with self._sf() as session: ... await session.commit()` 这种"方法级 session"模式（逐方法贴 sql.py 代码），对比 checkpointer 的长寿命池——这正是 Feedback"轻"、没有关机顺序麻烦、不进 AsyncExitStack 的根本原因。点明它对 AsyncExitStack 的"缺席"是有意的

- **麻烦 4：多租户隔离——谁的分只能谁看/谁删（resolve_user_id + AUTO）**
  - 场景：A 看不到 B 的打分、删不掉 B 的记录
  - 朴素：`WHERE thread_id AND run_id` 不带 user_id，全表串台
  - 解决：每个方法第一行 `resolve_user_id(user_id, ...)`（贴 user_context.py:166-195），AUTO→从 contextvar 取登录用户；过滤条件 `if resolved_user_id is not None: stmt.where(user_id == resolved_user_id)`（贴 list_by_run）。讲 `get(feedback_id)` 里的"不是你的记录当不存在"（返回 None 而非报错，防枚举攻击）。显式 None 通道留给 migration/CLI

- **麻烦 5：upsert 幂等 + 唯一约束——一人一票，不重复**
  - 场景：用户点了赞、又点踩；前端连点两次
  - 朴素：纯 INSERT，连点产生两条打分记录
  - 解决：① ORM 层 `UniqueConstraint("thread_id","run_id","user_id", name="uq_feedback_thread_run_user")`（贴 model.py:16）兜底 ② 仓库 `upsert`（sql.py:127-165）先 SELECT 再 UPDATE/INSERT；PUT 路由（feedback.py:61-89）是幂等语义。讲"DB 唯一约束是最后一道防线，upsert 是乐观路径"

- **麻烦 6：读侧 enrichment——不让打分查询拖垮消息列表（防 N+1）**
  - 场景：列出整个 thread 的消息，每条 AI 消息要带上"用户对它打了几分"
  - 朴素：循环每条消息查一次 `list_by_run`（N+1 查询）
  - 解决：`list_by_thread_grouped`（sql.py:190-203，一次查全 thread，按 run_id 分组成 dict）和 `list_by_run_ids`（sql.py:205-224，按一批 run_id `IN` 查）。贴 thread_runs.py:732-755 和 855-871 的消费代码——先算出"哪些 run 有 AI 消息要带 feedback"，再一次性批量查，再 in-memory 拼回。点明 `if last_ai_per_run:` / `if feedback_run_ids:` 两个守卫：没有 AI 消息就不查，省掉空查询。`aggregate_by_run`（sql.py:226-240）顺带讲数据库侧 `case/sum/count` 聚合 vs Python 侧循环

**第 3 步：把 6 个麻烦的本质串起来**

- 一句话本质：`get_feedback_repo` 把"反馈这个**可选**功能"的可用性边界、进程级单例、用户隔离、幂等、读侧聚合，**全部收口在 `app.state.feedback_repo` 这一个 None-able 单例 + `_require` 503 闸**里。
- 对照表（维度 | 朴素写法 | 真实写法），仿姊妹篇 §3
- 与前三篇的差别总结：前三篇解决"进程级资源必须活久且正确关停"；本篇解决"功能本就可选，要诚实地表达它的可用/不可用，且在可用时保证隔离与幂等"。一句金句收尾。
