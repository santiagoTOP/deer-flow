## 核心立意（文档的一句话主旨）

> **为什么"创建一个 run"不是路由里 `record.task = asyncio.create_task(agent.astream(...))` 一句话，而要一个 ~160 行的 `start_run` 编排函数？**

朴素写法在 6 个横切关注点上都会出问题：鉴权归属 / 模型白名单 / 并发策略 / thread 元信息 / config 加固 / task 注册与上下文还原。`start_run` 就是把这 6 件事集中处理完，吐出一个干净的 `RunRecord`，让三个路由（`create` 立即 JSON / `stream` 内联 SSE / `wait` 阻塞）能共享同一套启动逻辑、各自只操心"响应怎么包"。

## 文档结构（对标 run-manager-deep-dive.md）

**标题**：`start_run` 深度讲解：为什么"创建一个 run"不是路由里一句话，而要一个编排函数

**开篇**：交代与两篇姊妹篇的关系——`stream-bridge-deep-dive` 讲 `bridge`（事件流那一半）、`run-manager-deep-dive` 讲 `run_mgr`（执行+状态那一半）；本篇讲紧挨它们的 `start_run`——**run 是怎么被启动起来的**：从 HTTP 请求到 `asyncio.create_task` 之间发生了什么。

**第 0 步：前置概念**（快速带过与姊妹篇重叠的，重点讲本篇独有的）
- 0.1 三段架构：路由（薄）→ 服务 `services.py`（编排）→ `runtime`（执行）。`start_run` 是"编排层"，所以 6 个 call site 共享它。
- 0.2 `contextvar` / `set_current_user`——异步里的隐式上下文，跨 `await` 传 owner，为什么不能靠参数。
- 0.3 `owner_user_id` / `trusted_internal` / `auth_source`——多租户归属，内部调用者（IM/调度器）如何追溯真实用户。
- 0.4 `goal_thread_lock`（`runtime/goal.py:68`）——跨协程串行化同一 thread 的创建（带 `weakref.WeakKeyDictionary` 按 loop 隔离的细节）。
- 0.5 `RunnableConfig` & `configurable`——LangGraph 运行配置，`start_run` 花近一半篇幅在组装它。
- 0.6 外部 vs 内部调用者——安全边界，决定 context key 能否带、input 怎么 normalize。

**第 1 步：朴素写法长什么样（反面教材）**
贴一个 ~6 行的 `create_run_naive`（构造 agent → 直接 `create_task(agent.astream(...))` → 返回 record），逐行解释，然后点破它漏掉的 6 件事，引出第 2 步。

**第 2 步：6 个麻烦逐一展开**（每个都是「场景 / 朴素写法为什么做不到 / start_run 怎么解决」三段式，贴 `services.py:608-770` 真实代码逐行讲）
- **麻烦 1 · 鉴权与归属**：`check_access` + `get_trusted_internal_owner_user_id` + 内部调用者二次鉴权（`services.py:640-656`）。朴素写法谁都能在别人 thread 上开 run。
- **麻烦 2 · 模型白名单**：`get_app_config().get_model_config(model_name)` → 400（`services.py:624-636`）。朴素写法用户能指定任意模型绕过计费。
- **麻烦 3 · 多任务策略下的创建**：`goal_thread_lock(thread_id)` + `run_mgr.create_or_reject(...)` + `ConflictError→409`/`UnsupportedStrategyError→501`（`services.py:674-687`）。**承接** `run-manager-deep-dive` 麻烦 3（复述结论不重复细节），重点讲清楚 `start_run` 为什么在 RunManager 的内部锁之外**还要**多套一层 `goal_thread_lock`（串行化"创建 run + upsert thread_meta"这组跨 store 的 read-modify-write）。
- **麻烦 4 · thread_meta 的尽力而为 upsert**：`get/create/update_status` + 整段 `try/except: logger.warning`（`services.py:690-709`）。为什么"建 run"要顺带管"thread 是否注册"，以及为什么这个副作用失败**不能拖垮主流程**。
- **麻烦 5 · config 的层层加固**：逐层讲 `normalize_input`（外部 vs trusted_internal 的 input 清洗）→ `build_run_config` → `apply_checkpoint_to_run_config` → `merge_run_context_overrides` → `strip_internal_context_keys`（仅对外部调用者，剥掉内部 context key）→ `resolve_trusted_internal_owner_for_attribution` + `inject_authenticated_user_context`（`services.py:711-744`）。每一层点明它的安全/脱敏/归属目的。
- **麻烦 6 · record.task 延迟绑定 + contextvar 还原**：`create_or_reject` 返回时 `task=None`，`asyncio.create_task(run_agent(...))` 之后才 `record.task = task`（`services.py:746-761`）——为什么这个 task 不"野"（因为 record 已在 `create_or_reject` 里注册进 RunManager 的 `_runs`，承接姊妹篇麻烦 1）；以及 `finally: reset_current_user(owner_context_token)`（`services.py:766-768`）为什么必须配对、防止 owner contextvar 泄漏到下一个请求。

**第 3 步：一个 record 三种命——create / stream / wait**
讲同一个 `record = await start_run(...)` 在三个路由里如何被消费：
- `POST /{tid}/runs`（`thread_runs.py:488` `create_run`）：立即返回 `_record_to_response(record)`，task 在后台跑，客户端稍后连 `join`/`stream`。
- `POST /{tid}/runs/stream`（`thread_runs.py:496` `stream_run`）：包成 `StreamingResponse(sse_consumer(...))` 内联 SSE，带 `Content-Location` 头。
- `POST /{tid}/runs/wait`（`thread_runs.py:524` `wait_run`）：`await wait_for_run_completion(...)` 阻塞到 `END_SENTINEL`，返回 checkpoint。
点出**三个路由能共享 `start_run` 的根本原因**：横切关注点已全前置，路由只管响应形状。顺带提 `runs.py` 的 stateless 版本与 `launch_scheduled_thread_run`（`services.py:824`，body 是 `SimpleNamespace`），合计 6 个 call site。

**第 4 步：把本质串起来**
对照表（朴素写法 vs `start_run` 处理点），三姊妹篇关系图（`bridge` 解耦事件流 / `run_mgr` 解耦执行+状态 / `start_run` 是"安全启动"的编排阀门），收尾呼应开头那行 `record = await start_run(body, thread_id, request)`。
