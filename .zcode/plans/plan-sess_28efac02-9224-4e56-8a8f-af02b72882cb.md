### `## 第 1 步：朴素写法长什么样`
反面教材：路由里直接 `async for chunk in agent.astream(input, stream_mode="values"): yield chunk`，逐行解释，点破根本病根——**它假设"这次 run 就是这次 HTTP 请求"**：不能 rollback（没预拍快照）、不能被取消（没人检查 abort）、LLM 挂了会伪装成成功（没人查 fallback marker）、异常一路冒泡流就挂了（没 finally 收尾）。

### `## 第 2 步：6 个麻烦逐一展开`
每个 `### 麻烦 N` 都含 `#### 场景` / `#### 朴素写法为什么做不到` / `#### run_agent 怎么解决的` 三段，逐行贴真实代码解释：

- **麻烦 1：run 要活得比 HTTP 请求久，事件得走 Bridge 而不是 HTTP 响应**
  讲 `worker.py:350-357` publish metadata、`_stream_once`(490-525) 里每个 chunk 都 `bridge.publish`(502/523) 而不是 yield；串到 `services.py:746-760` 的 `create_task` + `record.task = task`(761)，说明为什么 worker 必须是后台 task、事件必须经 Bridge。

- **麻烦 2：用户要"打断重来"——rollback / interrupt 必须预先拍快照**
  讲 `worker.py:331-347` 跑前 `checkpointer.aget_tuple` + `copy.deepcopy` 存 `pre_run_snapshot`/`pre_run_checkpoint_id`；`320-328` 拍 workspace 快照；最后落点 `_rollback_to_pre_run_checkpoint`(1058-1148) 怎么把快照重写成新 checkpoint。讲清 interrupt（保留 checkpoint）vs rollback（回滚到跑前）的区别。

- **麻烦 3：agent 要会"自我追问"——goal continuation 隐藏轮循环**
  讲 `worker.py:527-550` 的结构：先跑用户那一轮 `_stream_once(graph_input,...)`(534)，再 `while` 循环调 `_prepare_goal_continuation_input`(866-1055) 判断要不要再来一轮隐藏的 goal-evaluator 续跑；讲循环退出条件(535)、`_continuation_runnable_config`(411-418) 为什么续跑要清 `checkpoint_id`。

- **麻烦 4：中途喊停——abort_event 协作式取消的双路径**
  讲 `worker.py:497、513` 流循环里 `record.abort_event.is_set()` 主动检查（主动 > 被动）；`552-571` 正常路径里检测到 abort 后按 `abort_action` 走 rollback/interrupt；`596-615` `except asyncio.CancelledError` 被动路径做**一模一样**的收尾；点明 `set_finalizing`(554/597) + manager 的 `wait_for_prior_finalizing`(298) 怎么配合多任务策略。

- **麻烦 5：LLM 挂了但看着像"正常结束"——error fallback marker 检测 + 历史去重**
  讲 model-call middleware 失败时往消息上贴 `deerflow_error_fallback` 标记；`worker.py:500/521` 流循环里 `_extract_llm_error_fallback_message`(1466-1522) 扫 chunk 抓 marker；`572-577` 抓到就把 run 标 error 而不是 success；专门讲 `pre_existing_message_ids`(282, 344, 368) 这层"历史去重"——为什么 LangGraph 重放历史会让"上一次 run 的旧 marker"误伤本次 run（`_try_extract_from_message` 1440-1463 的过滤）。

- **麻烦 6：不管怎么收场，流必须有终、状态都得落——finally 全收尾**
  讲 `worker.py:630-719` 这一大块 finally：`subagent_events.flush()`(633-634)、`record_workspace_changes`(636-646)、journal flush + `update_run_completion`(649-660) 持久化 token 用量、`_ensure_interrupted_title`(662-668)、标题回写 thread_store(671-681)、`_persist_run_duration`(685-700)、thread 状态更新(703-708)、`on_run_completed` 钩子(710-714)、清 finalizing(715-716)；最后两行是命门——`bridge.publish_end`(718) 保证订阅者一定收到终止符不会傻等、`asyncio.create_task(bridge.cleanup(..., delay=60))`(719) 延迟清理给迟到的订阅者留窗口。

### `## 第 3 步：把 6 个麻烦的本质串起来`
复述根本病根（朴素写法把"执行"焊死在"请求"里），用对比表格（HTTP 请求 vs agent 执行，沿寿命/取消/失败语义/可恢复/终态维度），把 6 个麻烦一一对应到 `run_agent` 的 6 个代码区域收口，结尾回到 `asyncio.create_task(run_agent(...))` 那一行，呼应三足鼎立。
